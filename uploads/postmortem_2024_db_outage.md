## 根本原因分析

### 直接原因

**数据库主节点磁盘写满** 是事件的起点，触发了一系列连锁故障：

1. **磁盘告警未及时处理：** DiskSpaceLow（80%）告警在 2 天前已触发，但被归类为 Warning 处理，未引起足够重视。直到磁盘写满（100%）触发 Critical 才开始应急。

2. **binlog 清理策略失效：** 自动清理脚本依赖 `PURGE BINARY LOGS BEFORE` 语句，但当时主从复制延迟超出了 `expire_logs_days` 设置，已被清理的 binlog 实际上从节点还未消费，导致清理脚本执行失败并静默退出。

3. **主从切换后应用未自动感知：** 数据库高可用使用 Keepalived VIP 漂移，但应用层的数据库连接池缓存了旧的连接，切换后旧连接全部失效。应用层缺少连接失效检测和自动重连机制（`pool_pre_ping` 未开启）。

4. **Milvus 磁盘问题作为隐患一并暴露：** etcd 默认保留大量历史快照（默认 100 个），长期运行后日志占用磁盘较多，在此次重启过程中才被发现。

### 根因链

```
磁盘告警未处理（2天前）
    ↓
主节点磁盘写满 → MySQL 停止写入
    ↓
主从复制中断 → HA 触发主从切换
    ↓
连接池未感知切换 → 全部连接失效
    ↓
应用层写入全部失败（P0）
    ↓
重启应用时发现 Milvus/etcd 磁盘异常（隐患暴露）
    ↓
Milvus 服务异常 → 知识库检索失败（额外影响）
```

## 经验教训

1. **Warning 告警必须有 SLA**：磁盘 Warning 在 2 天前已触发，但没有明确的处理时限，最终酿成 P0。所有 Warning 级别告警需要规定最长响应时间。

2. **连接池 pool_pre_ping 是必须项**：不开启时，主从切换、网络抖动等场景都会导致连接静默失效，等到应用报错才能发现。开启后性能损耗极小（每次连接多一次 SELECT 1 验证）。

3. **故障往往是隐患集合的暴露**：Milvus/etcd 磁盘问题本来和数据库故障无关，但在同一次事件中一并暴露出来，说明日常巡检存在死角。

4. **磁盘容量预测比阈值告警更重要**：`DiskSpaceLow`（80%）触发时，磁盘可能还有很长时间才会满；但如果磁盘在以每小时 5GB 的速度增长，4 小时后就会写满。预测性告警比阈值告警更有实际意义。

5. **CPU 飙高有时是果，不是因**：本次事件中 CPU 使用率 90% 是因为请求积压重试，根因是磁盘和数据库问题。看到高 CPU 告警要先问"是什么在消耗 CPU"，而不是直接去看进程。
