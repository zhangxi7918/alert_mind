# 容量规划指南

_负责人：基础设施组 | 更新周期：每季度_

---

## 容量评估触发条件

| 触发条件 | 评估范围 |
|----------|---------|
| 大促活动前 30 天 | 全链路容量评估 |
| CPU/内存水位连续 7 天 > 70% | 对应服务扩容评估 |
| 新业务上线 | 资源需求估算 |
| 成本优化专项 | 全链路缩容评估 |
| 季度例行 | 全局容量审视 |

## 核心指标基准

### 计算资源

| 服务类型 | CPU 水位目标 | 内存水位目标 | 说明 |
|----------|------------|------------|------|
| 无状态 API | 60-70% | 70-80% | 留 30% 余量应对突发 |
| 数据库（主） | 50-60% | 75-85% | 主库水位要更保守 |
| 消息队列 | 40-60% | 60-75% | 堆积处理需要额外内存 |
| 缓存（Redis） | 30-50% | 70-85% | 内存是 Redis 核心资源 |
| 批处理任务 | 70-90% | 70-85% | 可以充分利用，有弹性窗口 |

### 存储资源

| 存储类型 | 告警阈值 | 扩容阈值 | 扩容周期 |
|----------|---------|---------|---------|
| 系统盘 | 80% | 70% | 2 周内完成 |
| 数据盘（MySQL） | 70% | 60% | 1 个月内完成 |
| 数据盘（Kafka） | 75% | 65% | 2 周内完成 |
| 对象存储（OSS） | 85% | 75% | 按需扩，无上限 |

## 峰值流量估算方法

**历史数据法**（有历史数据时使用）

```
预期峰值 QPS = 历史同期峰值 × 业务增长系数 × 安全冗余系数

业务增长系数 = 根据业务预测，通常由产品/业务提供
安全冗余系数 = 1.3 ~ 2.0（大促建议 2.0）
```

**大促专项估算公式**

```
大促峰值 = 日常峰值 × 大促流量倍数

大促流量倍数参考（历史数据）：
  双11：日常峰值的 8-12 倍
  618：日常峰值的 4-6 倍
  黑五/双12：日常峰值的 3-5 倍
```

## 资源需求计算

### CPU

```
所需核心数 = (峰值 QPS × 单请求 CPU 时间ms) / 1000 / 目标水位

示例：
  峰值 QPS = 5000
  单请求平均 CPU 时间 = 10ms
  目标水位 = 0.6

所需核心数 = (5000 × 10) / 1000 / 0.6 = 83.3 → 向上取整 = 90 核
```

### 内存

```
所需内存(GB) = (实例数 × 单实例内存占用GB) / 目标水位

单实例内存占用 = 压测观测值（非估算）
```

### 带宽

```
所需带宽(Mbps) = 峰值 QPS × 平均响应体积(KB) × 8 / 1024 × 安全系数

安全系数通常取 1.5
```

## 压测要求

容量规划结果必须经过压测验证，验证指标：

| 指标 | 通过标准 |
|------|---------|
| 目标 QPS 下错误率 | < 0.1% |
| P99 延迟 | 不超过 SLO 定义阈值 |
| CPU 水位 | < 目标水位 × 1.1 |
| 内存水位 | < 目标水位 × 1.05 |
| 无 OOM/Core dump | 零容忍 |

## 扩容申请流程

1. 填写容量评估表（模板见内网 wiki）
2. 提交至 #infra-capacity 频道，@值班架构师
3. 评估周期：常规申请 3 个工作日，大促专项 5 个工作日
4. 批准后由基础设施组执行，申请方验收

**紧急扩容**（P1 事故中）：直接联系值班工程师，走紧急通道，事后补材料。
