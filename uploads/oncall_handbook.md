# 基础设施组值班手册

_本文档由基础设施组维护，每季度 review 一次。如有疑问联系 @infra-oncall 或在 #infra-ops 频道提问。_

---

## 值班职责

值班工程师负责在轮值周期内（每周一早 9 点交班）处理以下事项：

所有 PagerDuty 告警的一线响应。目标响应时间：P0 < 5 分钟，P1 < 15 分钟，P2 < 1 小时。P3/P4 告警在工作时间内处理即可，不需要半夜爬起来。

值班期间如果有计划变更（部署、配置修改），需要在 #change-announcements 频道通知，并确认有回滚方案。这不是流程要求，是真的被坑过才加的规矩——2024年3月那次数据库迁移就是因为没通知值班人导致告警风暴处理混乱了两个小时。

收到告警后，无论是否在5分钟内解决，都要在 #oncall-log 里发一条消息说明情况。格式不重要，能让下一班人知道发生了什么就行。

## 告警分级标准

P0 是生产环境完全不可用，或者核心支付链路中断，或者数据丢失正在发生。P0 需要立刻叫醒所有人，包括业务负责人。不要自己扛，不要等着看会不会自己好。

P1 是生产环境严重降级，主要功能受影响，大量用户报错。P1 需要在 15 分钟内有人接手处理，超过 30 分钟没有进展需要升级到 TL。

P2 是部分功能受影响，有降级但系统整体可用。工作时间内处理，非工作时间可以等到次日早上。

P3/P4 是轻微问题或者潜在风险，正常排期处理。

具体的告警和等级映射见 reference_alert_rules.md，这里不重复了。

## 交班流程

交班不是发个消息说"我下班了"，要做以下几件事：

**接班前 30 分钟**，接班人登录 PagerDuty 确认已接管告警轮次。

当前有未解决的告警或进行中的事故时，口头或视频同步一次，不要只靠文字。2024 年有过一次交班时 Slack 消息没看到，导致 P1 事故处理中断了 20 分钟，后来加了这条规定。

当前值班周期内所有 P2 以上事件要有记录，接班人要确认已读。记录在内网 wiki 的《值班日志》页面，不要放在私聊里。

## 常用命令和工具

Grafana 看板地址：见公司内网文档（此处不写，外泄风险）

查看系统整体健康：
```bash
# 所有命名空间的 Pod 状态
kubectl get pods -A | grep -v Running | grep -v Completed

# 节点状态
kubectl get nodes

# 最近 1 小时的告警历史（Alertmanager）
curl -s http://alertmanager:9093/api/v1/alerts | jq '.data[] | select(.status.state=="active")'
```

查看日志（我们用 Loki，不直接看文件）：
```bash
# 用 logcli（已安装在跳板机）
logcli query '{namespace="production",app="api-gateway"}' --since=1h --limit=100
```

## 升级路径

遇到拿不准的情况，升级不是软弱，是正确做法。

基础设施 TL（技术负责人）的联系方式在 PagerDuty 的 escalation policy 里。工作时间内直接 @ Slack，非工作时间通过 PagerDuty 升级。

业务线 on-call 名单每月在 #oncall-schedule 更新，影响到具体业务时需要同时通知对应业务侧 on-call。

安全相关的事故（数据泄露、异常访问、DDoS）走单独的安全响应流程，见《安全事故响应手册》（内网 wiki，此处略）。

## 已知的坑

- Prometheus 偶尔会出现 TSDB 写入延迟，表现为告警比实际晚 3-5 分钟触发。所以看到 Grafana 上指标已经恢复但告警还在 firing 的情况，等 5 分钟再判断。

- 夜间 3-4 点有个定时任务（数据归档）会让 MySQL 慢查询率短暂升高，持续 10 分钟左右，这是正常的，不需要处理。已经加了 silence，理论上不会告警，但如果看到要知道原因。

- k8s 1.27 升级之后 HPA 的缩容有个 bug，在低流量时段可能会过激缩容，导致下一个高峰来时扩容不及时。平台组正在跟进，临时方案是把 HPA 的 `scaleDown.stabilizationWindowSeconds` 调高了，但不要轻易改这个参数。
